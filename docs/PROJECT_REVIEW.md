# 个人量化项目审查与改进建议

> 日期：2026-08-23  
> 范围：`/Users/henry/projects/quant` 当前项目结构、策略回测、Paper 交易、Trading Team 决策流、数据流与控制台。

## 总体判断

这个项目现在适合做“研究和流程演示”，还不适合把任何输出当成可交易信号。

最大问题不是代码能不能跑，而是事实源混乱、回测门槛太松、Paper 语义不可信。当前已经出现“审批文件批准买入”和“实际执行全观望”并存的情况。继续往上叠加 LLM 角色、飞书推送、控制台审批，只会放大底层账本和信号一致性的问题。

一句话评价：公司化流程和多智能体角色做得太快，底层交易账本、信号一致性、验证门禁还没站稳。先少做角色包装，多做可复现的净值、订单、数据和风控闭环。

## 关键问题

### 1. 决策事实源已经分裂

同一天存在多个互相冲突的决策源：

- `trading_team/decisions/2026-08-22/decision.json`：全观望，且 `pm_status=approved`。
- `trading_team/outputs/2026-08-22/plan.json`：平安、宁德包含买入或条件买入计划。
- `trading_team/loops/approvals.json`：同一天 5 个提案全部被批准。
- `trading_team/team.db`：执行结果是 0 笔交易。

这不是展示层小问题，而是交易系统的大问题。审批和执行读的不是同一个事实源，就会出现“用户以为已批准执行，系统实际没有执行”或反过来的风险。

改进方向：

- 只保留一个主决策源。建议二选一：
  - 以 `team.db` 为主事实源；
  - 或以 `decisions/YYYY-MM-DD/decision.json` 为主事实源。
- `plan.json`、`approvals.json`、控制台展示、飞书卡片只能是派生产物。
- 审批后必须同步更新主事实源，再允许执行。
- 每次执行前做一致性校验：同日 `decision.json`、`plan.json`、approval、team.db 不一致则 fail closed。

### 2. Paper 阶段没有真正执行 live 策略

`pipeline/stage_paper.py` 里直接硬编码了股票池、动量窗口、持仓数量和均线风控参数。它只是检查注册表里有没有 live 策略，并没有调用 live 策略文件本身。

结果是：

- `status.json` 里显示哪个策略 live，并不等于 Paper 实际跑哪个策略。
- 策略文件改了，Paper 逻辑可能没变。
- Paper 表现无法证明 live 策略真实可运行。

改进方向：

- 抽出统一信号接口，例如：

```python
def generate_targets(as_of, portfolio, data, params):
    return targets
```

- Backtest、Paper、日报提案至少应共享同一套信号计算逻辑。
- `stage_paper.py` 不应复制策略参数，只负责：
  - 加载 live 策略；
  - 获取当前账户；
  - 调用策略生成目标持仓；
  - 模拟撮合并记账。

### 3. 回测门禁太宽，容易制造虚假信心

当前门禁类似：

- 年化收益 > 5%
- 最大回撤 < 30%
- 夏普 > 0.3

这个标准对 A 股策略太低。它只能证明策略没有明显崩掉，不能证明有可交易 alpha。

缺失项包括：

- 样本外测试；
- 滚动窗口稳定性；
- 参数扰动稳定性；
- 交易成本、滑点、冲击成本；
- 换手率；
- 停牌、涨跌停导致的无法成交；
- 相对沪深300的超额收益；
- 月度收益分布；
- 最长回撤恢复期；
- 最差单月、最差连续亏损；
- 持仓集中度和行业暴露。

改进方向：

- 门禁至少升级为：
  - 全样本和样本外都过；
  - 超额收益为正；
  - 年化超额收益、信息比率、最大回撤、换手成本全部达标；
  - 参数扰动后结论不反转；
  - 至少 3 个市场阶段分别统计。
- 不要让“同一策略不同包装”重复通过门禁。`momentum_rotation` 和 `momentum_stops(stop=none)` 本质近似，应合并为同一策略族。

### 4. 成交假设过于乐观

当前 Paper 和 LLM 执行器都使用“收盘价成交、免手续费、无 T+1 限制”的简化假设。

这对 A 股不是小误差，而是会改变策略排序的核心假设，尤其影响：

- 月度调仓；
- 止损；
- 缺口低开；
- 跌停无法卖出；
- 涨停无法买入；
- 停牌；
- T+1 卖出限制；
- 印花税和佣金。

改进方向：

- 信号日和成交日分离：用 T 日收盘生成信号，T+1 按可成交价格执行。
- 加入 A 股约束：
  - T+1；
  - 整手；
  - 涨跌停不可成交；
  - 停牌不可成交；
  - 佣金、印花税、过户费；
  - 买入用次日开盘或 VWAP 模拟，不要默认同日收盘成交。
- 止损不能只用收盘触发。至少要比较：
  - 收盘止损；
  - 次日开盘止损；
  - 跌停无法卖出的延迟止损。

### 5. 数据层不统一

项目中同时存在：

- RQAlpha 官方 bundle；
- `trading_team/context/<date>/` 外部采集数据；
- `patch_bundle_from_context.py` 试图把新鲜数据补进 bundle；
- 控制台和日报读取不同产物。

这会造成一个问题：同一日期、同一股票，在不同模块里使用不同价格、不同复权口径、不同最新交易日。

改进方向：

- 明确数据分层：
  - `raw_external_context`：外部接口原始采集；
  - `official_bundle`：RQAlpha 官方 bundle；
  - `patched_bundle`：补丁后的研究用 bundle；
  - `paper_prices`：Paper 实际成交价格源。
- patched bundle 必须带版本号和校验摘要。
- 补丁写入前必须校验：
  - 重叠日收盘价；
  - 前复权口径；
  - 涨跌停字段；
  - 成交额和成交量单位；
  - 指数和个股字段 dtype。
- 禁止静默混用不同数据源。

### 6. 没有真正的测试体系

目前项目更像“脚本 + 日志 + 手工观察”，缺少关键路径测试。语法能过不代表交易逻辑正确。

必须补测试的路径：

- 审批状态流转；
- 同日重复审批覆盖；
- approved/rejected/reduced 行为；
- `decision.json`、`plan.json`、`approvals.json` 一致性检查；
- 买入、卖出、持有、观望、回避解析；
- `position_pct` 字符串和数字解析；
- 现金不足时的下单调整；
- positions 重写前后的权益守恒；
- Paper 幂等；
- 回测门禁拒绝逻辑；
- 数据缺失时 fail closed；
- patched bundle dry-run 和拒写逻辑。

## 改进优先级

### P0：先止血

1. 冻结自动执行链路。
2. 统一决策事实源。
3. 给执行器加一致性校验。
4. 把 `plan.json` 中的字符串仓位改成结构化字段，例如：

```json
{
  "position_pct": 0.15,
  "entry_type": "limit_or_pullback",
  "entry": ["53.5", "52.2"],
  "condition": "高开超过3%不追"
}
```

5. `market_ok=false` 时禁止任何买入计划被标记为 approved executable。

### P1：修 Paper 的可信度

1. 从策略文件抽统一信号接口。
2. Paper 调用同一信号接口，不再硬编码策略。
3. 加入 T+1、费用、涨跌停、停牌和整手约束。
4. 每笔 Paper trade 记录：
   - 信号来源；
   - 数据源版本；
   - 计划价格；
   - 模拟成交价格；
   - 失败原因；
   - 是否因风控拒绝。

### P2：重做门禁

1. 加样本内/样本外拆分。
2. 加滚动回测。
3. 加参数扰动。
4. 加成本模型。
5. 策略族去重，禁止重复包装刷通过率。
6. 复盘报告展示失败样本，不只展示通过结果。

### P3：再做 LLM 交易团队

LLM 角色可以保留，但定位必须降级：

- 分析师只能生成研究观点；
- 交易员只能生成候选计划；
- 风控只能给约束；
- 最终可执行订单必须由确定性规则验证；
- LLM 输出不得直接写 Paper 账户。

建议把 LLM 提案分成三层：

1. `research_signal`：研究观点；
2. `trade_proposal`：候选计划；
3. `executable_order`：通过确定性风控后的可执行模拟订单。

只有第三层能进入 Paper。

## 建议的新验收标准

一个策略要从 research 进入 live/Paper，至少满足：

- 数据源和复权口径固定；
- 无未来函数；
- 同一信号接口能同时服务回测和 Paper；
- 样本外为正；
- 加成本后超额收益为正；
- 最大回撤低于阈值；
- 最差月、最长回撤恢复期可接受；
- 参数扰动后结果不崩；
- Paper 至少连续运行一个完整调仓周期；
- 所有交易有可复盘订单记录；
- 自动测试覆盖关键状态流。

## 最后结论

当前项目最需要的不是更多 Agent、更多页面或更多推送，而是交易系统的基本纪律：

- 一个事实源；
- 一个信号接口；
- 一个可信账本；
- 一个保守撮合模型；
- 一套会拒绝错误状态的测试。

这些打牢之后，LLM 交易团队才有意义。否则多智能体只是在给一个不稳定的账本制造更复杂的解释。
