## 目标

系统的首要产物不是“一个看起来合理的荐股结论”，而是一条可复核的证据链：

`数据版本 -> 角色输入 -> 角色产物 -> 计划版本 -> 审批版本 -> Paper 委托/成交 -> 反事实 -> 前向评价`

任何人都应能回答：这次结论使用了什么数据、谁做了什么、哪一步失败、重试复用了
什么、审批对应哪个计划版本、订单为何成交或未成交、收益属于真实 Paper 还是代理计算。

## 系统边界

- 研究和 Paper 默认允许自动运行。
- Live 始终需要人工审批，且审批必须绑定当前 `plan_hash`。
- 计划变化后旧审批失效。
- Multica 负责编排、角色身份、Issue/Run 历史和触发，不直接写审批或账户数据库。
- Python 确定性层负责数据闸门、A 股规则、计划校验、撮合、记账和反事实计算。
- LLM 只产生受 schema 约束的研究证据与提案，不拥有订单提交权限。

## 事实源

| 事实 | 唯一来源 | 不可替代来源 |
|---|---|---|
| 工作流和步骤状态 | `.runs/ledger.db` | 日志文本、文件是否存在 |
| 数据截至日和采集质量 | `context/<date>/manifest.json` + ledger `data_collect` | LLM 报告中的口述 |
| 日报生成版本 | `outputs/<date>/generation.json` + ledger `publish_generation` 哈希 | 仅存在的日报文件 |
| 提案版本 | `outputs/<date>/plan.json` + canonical `plan_hash` | Markdown 摘要 |
| 审批状态 | `decisions/<date>/decision.json` / 审批表 | 聊天确认 |
| Paper 成交 | Paper SQLite 账户与撮合事件 | 收盘涨跌、机会成本 |
| Paper 执行幂等 | `execution_receipts` 的执行日、计划哈希、行情输入/撮合版本哈希及凭据来源 | 是否存在委托（零委托也必须结算留痕） |
| 成交行情 | `replay_data/<date>.json` 的 `execution_bars.v2` 契约、原始记录和哈希 | 前复权 K 线、未带日期的快照、猜测的涨跌停比例 |
| 策略收益 | 严格撮合或明确标注的反事实结果 | 截图、回看式收益 |

## Loop Engineering 闭环

### 触发

- 交易日定时触发。
- 人工指定日期触发。
- Multica Issue/Autopilot 触发。

所有触发都写入 `trigger_source`。定时器“已启用”不等于运行成功，运行中心必须同时展示
最近运行、步骤状态、业务产物和下一次触发。

### Maker / Checker

- Maker：四类分析、研究综合、交易提案。
- Checker：数据质量、独立风险经理、审计验证器。
- 同一角色不能同时生成提案并声明提案通过。
- Checker 失败时保留 Maker 产物和错误，不用空报告覆盖。

### 恢复

每个角色步骤记录日期、模型、输入哈希、提示词哈希、输出哈希、产物路径、尝试次数和错误。
复用角色缓存时核对输入、章程、模型、报告内容和结构化响应哈希，同时保存实际模型输入。
整套日报通过 `generation.json` 绑定归档数据、观察池、七份角色章程、模型、报告、响应元数据和
canonical `plan_hash`，生成凭据自身的哈希记录到运行账本。目录原子发布后才能进入收尾；如果
发布后账本确认中断，重跑先验证整套证据，再补记完成，不必重复调用模型。

同一业务日期的日会采用进程文件锁，重复触发不能接管仍在工作的运行。强制重跑将旧输出及
未完成 staging 移至 `.runs/archive/<date>/<new-run-id>/`，保留旧版本。已有日报必须通过
manifest 和生成凭据核对才能复用；不匹配时记录失败，要求显式重新生成。没有生成凭据的历史
日报继续保留供查看和历史收尾，不补造生成记录，也不能作为一次新研究运行的成功证据。

enrich、backfill、index 等读取可变状态的步骤每次重检；finalize 和 outbox 分别负责自身的
版本幂等。估值、索引和推送之前，`verify_materialization` 强制核对 Live-pending 与 Paper
决策的日期及 `plan_hash`。任何复用或收尾异常都写入失败状态。

### 结算恢复

`daily_finalize` 使用与采集相同的 A 股交易日历，以 Asia/Shanghai 的 15:10 为当日完整
会话门槛；日历缺失、损坏或不覆盖业务日时失败关闭。休市和未完成会话仍可物化决策，但不做
成交重放或 Paper 结算。日历内容哈希、会话状态及请求模式共同绑定收尾输入版本。

已成功的收尾仅在决策、反事实 JSON/Markdown、重放行情及 Paper 账户证据校验一致时复用。
派生文件缺失或改动可重新生成；已结算账户、凭据或相关委托成交变化则停止，要求先核对账务，
不能通过重跑把变化追认为可信基线。批量 CLI 有任一天失败即返回非零退出码。

每个 Paper 账户通过 SQLite `BEGIN IMMEDIATE` 串行检查和提交执行凭据、委托、成交、持仓、
账户及估值，包括零委托日期。相同执行日、计划版本、撮合版本和原行情输入全部一致才允许
重复调用跳过；同日换计划、换行情或在较新账户状态上重执行旧日被拒绝。该事务保护不代表
多日期工作流、共享 accuracy/index 的并发已整体解决。

历史零委托账户只有在旧成功账本的 `plan_hash`、零委托/零成交结果和当天账户说明全部一致，
且当天确实没有订单/成交时，才迁入 `legacy_ledger_import` 凭据，记录来源 run 和实际迁入
时间。不补造历史执行时间，不重算旧持仓，不覆盖账务。
这种迁入只标记为 `legacy_account_only`，不认证其历史成交行情符合新版契约。旧委托或普通
执行凭据缺少行情输入时必须单独核对，不再仅凭存在委托就自动迁入成功凭据。

### 成交行情契约

Loop #27 将严格重放与双 Paper 的行情读取统一到 `trading_team/execution_bars.py`：

- 只接受指定已完成交易日的未复权行情。日期、OHLC、参考价、成交量、停牌状态和上下限均校验；
  数值缺失、NaN/Infinity、价格关系矛盾或复权口径不符时停止，不默认可成交。
- 来源顺序为同日归档收盘快照、本地 RQAlpha 原始 bundle、腾讯准确日期的收盘快照。
  不再用前复权历史 K 线补实际委托价格。旧日期没有完整原始数据时失败，不拼接当前涨跌停价。
- 保存来源记录、来源摘要、缓存整体哈希，并核对归一化行情确实来自该记录。哈希用于内容
  一致性与恢复，不是数据供应商真实性或无错误的独立保证。
- 采用数据源给出的当日参考价和实际涨跌停价，不以昨日普通收盘价或代码前缀推测特殊股票限制。
  沪深 300 是基准指数，其 `-1` 上下限占位值不作为股票限制使用。
- 来源没有独立停牌标志时，零成交量被保守视为不可成交；这是防误成交规则，不是已证实的
  交易所停牌事件。缺少该日行也不自动补成一条可交易行情。
- 显式上下限模式下，股票成交价按 0.01 元单位不利方向处理；滑点后越过当日上下限拒绝。
  旧研究模型的比例限制回退使用最小价格单位四舍五入，严格生产读取不依赖该比例回退。
- 缓存加同日进程锁并原子发布；已有行不被自动刷新。旧格式缓存保留原文件并报错，不能靠
  补一个版本号就升级为可信数据。正式迁移必须先归档、在隔离目录重放并核对旧账。

新 Paper 凭据保存实际行情字段、费用配置、滑点和 `daily_bar_t1.v2` 版本，以及对应哈希。
重试必须复核原始标的，即使持仓已卖出；新增加的不相关缓存标的不导致重复记账。外层收尾
输入哈希也绑定撮合配置，不能绕过内部复核。修改撮合语义时必须更新模型版本。

反事实报告标为 `DAILY_BAR_PROXY`。只有经过严格读取和缓存交叉校验的正式写入入口才标记
`market_data_schema` 与 `market_data_hash`；直接向纯计算函数传入行情不获得来源认证。
日线触价不能证明排队成交、成交容量或盘中先后顺序，不能视作实盘成交回报。

日会收尾只处理指定业务日及上一交易日；缺计划的会话显式记为 skipped。无日期的独立历史
批量命令仍会审计全历史并暴露失败，不在每次新日报中隐式迁移旧数据。

### 资金时点与估值

Loop #28 修复了“当日收盘净值决定盘中买入数量”的未来信息问题。双 Paper 和原审批执行器
均使用执行前现金加原持仓数量乘 `prev_close` 参考价作为建仓资金基准；收盘价只用于执行后
估值。该参考价在除权日未必等同普通前日收盘价，分红和送转的账户权益事件仍须单独实现。
缺少持仓参考价时拒绝执行，不用成本价补齐，也不忽略非本次交易标的的旧持仓。
新凭据保存 `sizing_basis` 的现金、持仓、参考价和基准权益，撮合版本升级为 `daily_bar_t1.v3`。

账户页面及估值落库不再使用 `technical_*.json` 的技术分析收盘价。它们只读
`execution_bars.v2` 缓存或通过同一契约验证的归档原始收盘快照，保留归一化行情和来源证据；
GET 不访问行情网络，不创建缓存，不恢复账本。交易日历、上海 15:10 门槛、请求日和行情截至日
共同限制可用数据。缺日期、坏缓存、未知复权口径和非法数值均不能作为估值。

行情早于账户最新状态或任一现持仓买入日时，不把当前现金和持仓倒记到旧行情日；缺失任一
持仓价格时权益未知。纯现金账户仍可显示现金权益，但这不表示行情已通过核验。没有合格行情时
不返回一个伪装成已验证的行情日期或来源标签。

估值写入先只读确认账户存在且结构有效，不能把空数据库初始化为十万元。每个账户使用
`BEGIN IMMEDIATE` 覆盖状态读取和写入，读取快照本身使用一致读事务。撮合与独立估值复用
同一行构造函数；只有账户、行情字段、持仓、版本关联及来源口径相符才可幂等复用。已有行
冲突时要求核对，不以 `INSERT OR IGNORE` 掩盖变化；未知估值跳过，不冻结成永久空值记录。

## Multica 接入

仓库中的 `multica/workspace.json` 定义项目、Squad、角色和状态存储，
`multica/runbooks/daily-research.md` 定义阶段屏障与恢复规则，
`trading_team.multica_adapter` 负责状态检查、Issue 准备和派发。

目标是 Squad 只唤醒 Research Lead；Leader 根据阶段把工作路由给 Data Quality、Market Analysts、
Strategy Research、Paper Trader、Risk Manager 和 Audit Verifier。Squad 不自动把同一任务广播给
所有角色，避免重复产出和触发循环。当前完整发布器内部的七个LLM角色不等于七个远端任务；
逐角色有界交接及独立远端审阅仍待实现和真实验收。完整发布入口只接受Research Lead，
其他角色不得重跑整个命令来代替分工。

本地命令：

```bash
.venv/bin/python -m trading_team.multica_adapter status
.venv/bin/python -m trading_team.multica_adapter prepare --date YYYY-MM-DD
.venv/bin/python -m trading_team.multica_adapter bootstrap --runtime-id <id> --daemon-id <id>
.venv/bin/python -m trading_team.multica_adapter dispatch --date YYYY-MM-DD
```

`bootstrap` 幂等创建或复用 Project、本地目录资源、七个 Agents、Squad、Autopilot 和交易日
schedule，并将非敏感资源 ID 写入本地状态。`dispatch` 在 CLI 未安装、未登录、daemon 未运行
或资源尚未真实落地时失败关闭；仓库中的 `workspace.json` 本身不是接入成功证据。

### 执行身份与重试记录

`kimi_daily --trigger-source multica` 必须同时传入 `--multica-issue-id <current-issue-id>`。
daemon 提供 `MULTICA_TASK_ID`、`MULTICA_AGENT_ID`、`MULTICA_WORKSPACE_ID`，不提供之前
代码假定的 `MULTICA_ISSUE_ID`。命令读取远端 Issue 和 execution history，核对业务日期、项目、
workspace、团队 Agent 及 running task 后才可调用模型，身份错误会在本地账本记录失败。
接口依据为 [Multica daemon 官方源码](https://github.com/multica-ai/multica/blob/main/server/internal/daemon/daemon.go)
及已安装 CLI 的 `issue get/runs --help`。

`workflow_attempts` 逐次保留触发来源、远端身份、核验时间、开始/结束时间、状态和错误，
`step_runs.workflow_attempt` 将步骤关联到具体尝试。重试不覆盖之前的失败来源；旧运行没有
尝试级历史时不补造。核验记录只表示当时远端身份匹配，不代表远端任务永远在线，也不证明七角色
均已实际执行。Multica token、完整环境和密钥不进入这些记录。

只允许 Audit Verifier 执行的受限集成验收入口：

```bash
.venv/bin/python -m trading_team.multica_adapter audit --date <business-date> --issue-id <current-issue-id>
```

该命令须处于标题为 `A-share integration audit <business-date>` 的真实运行任务中。

## 双账户备份与隔离恢复

2026-09-22 Loop #31 增加 `paper_recovery`，保护的是当前 LLM 双 Paper 账户事实，而非重新
计算或认证旧成交。账户本身通过 SQLite 只读连接读取，不调用 `_db` 初始化或迁移生产库。
备份采用 [SQLite Online Backup API](https://sqlite.org/backup.html)，包含 WAL 中已提交数据，
不直接复制正在使用的主数据库文件，不带入未提交事务。

```bash
.venv/bin/python -m trading_team.paper_recovery backup --target trading_team/.runs/backups/<new-id>
.venv/bin/python -m trading_team.paper_recovery verify --source <backup-directory> --manifest-hash <returned-sha256>
.venv/bin/python -m trading_team.paper_recovery restore --source <backup-directory> --manifest-hash <returned-sha256> --target /private/tmp/<new-recovery-root>
```

命令失败返回非零码。保存 backup 返回的 `manifest_hash`，verify/restore 必须提供该哈希，
不能仅凭目录存在或重新计算一个未知来源的哈希认定备份可信。哈希是完整性核验，不是签名或
防同权限管理员篡改的保证。备份没有自动定时执行，也没有自动替换生产库。

一致性与失败边界：

- 双账户执行、当前估值写入、旧零委托凭据迁入与备份共用按路径排序的文件锁；占用时拒绝
  重叠操作，不能在正常双账户调用的两个提交之间拍摄备份。锁不被删除以避免 inode 竞态。
- 每个源库保持 SQLite 读事务；全表行顺序、列、schema、行数和摘要与目标逐项比较。
  另核对 SQLite 完整性、外键及文件哈希；`sqlite_sequence` 也被保存。
- 复制后核对源 `data_version` 和 inode，检测复制窗口内绕过应用锁的提交/替换。
  这不授权外部直接 SQL 写入，也不把两个 SQLite 库变成跨库原子事务。
- `pair_alignment=aligned` 仅表示两账户最后记账日期相同，不是资金、成交或计划语义已核对。
  崩溃后日期不同的事实也会保留，但明确标为 `requires_reconciliation`。
- 全部内容核对并刷盘后才发布 `manifest.json`；部分失败目录保留用于调查，不可当成功备份。
  恢复先验证源，再写新目录，验证目标后最后发布 `restore.json`。已有目录一律拒绝覆盖。
- 恢复禁止指向原项目目录或备份内部；恢复标记为 `verified_isolated`、
  `execution_authorized=false`，不修改生产路径，不启动任何服务或继续执行交易。
- 缺少新版凭据的历史日被列入 `unreceipted_days`；即使已有凭据，整个备份仍标记
  `execution_evidence=not_recertified`，不把复制正确等同于历史成交正确。

范围明确限定 `paper_accounts_only`：不包含旧策略 `paper.db`、Live、计划、审批、工作流账本、
行情、密钥和环境。完整业务恢复还需要这些独立证据的版本一致性核对及人工切换验收；本机
同盘备份也不等于异地灾备。文件锁覆盖上述公开双账户入口，不覆盖手工 SQL 或内部私有函数。

真实演练记录：`docs/audits/2026-09-22-paper-recovery.json`。备份位于

## 十进制撮合版本

2026-09-22 Loop #33 将当前模型升级为 `daily_bar_t1.v4`。适用范围仍是本系统的 A 股股票

本系统明确选择的保守滑点假设，不是交易所对模拟收益的认可。

- 滑点乘法从输入开始使用 `Decimal`，不先经过二进制浮点乘法；买入向上、卖出向下量化到分。
- 有无显式涨跌停价均使用相同价格精度。限价自身必须为合法分单位，不将非法申报价静默改价。

- 提供当日高低价时，滑点后的价格不得超出该区间；拒绝不能由历史价格支持的成交，不将价格
  强行截回高低价后继续记账。无显式实际上下限的旧研究输入仍不能当作严格交易证据。
